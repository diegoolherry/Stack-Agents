## 2. Patrones existentes
- **Etapa condicional por trigger:** Security Auditor solo corre si el diff toca `scripts/security-trigger.config.json`; UX/UI solo si la feature tiene interfaz. Ambos son el precedente directo para una etapa QA que solo aplique a features web/UI.
- **Degradación graceful sin preflight:** Reviewer documenta ausencia de `reports/<feature>-preflight.md`, corre tests manualmente y no rechaza por falta de métricas. Precedente para QA opcional sin dependencia dura.
- **Un reporte por etapa en `reports/<feature>-<etapa>.md`:** Reviewer y Security Auditor escriben ahí con permiso `edit: reports/**` y retornan solo la ruta. El template de body PR de `scm` ya lista reportes; hoy no tiene slot QA.
- **Permisos mínimos por agente (solo-opencode):** cada etapa es un par `agents/<rol>.md` (frontmatter `description/mode/permissions`) + `skills/<rol>/SKILL.md` (rol, inputs, proceso, output, reglas). QA encajaría en ese molde sin tocar `.claude/` ni `.gemini/`.
- **Orden actual Full:** `Implementer(s) → Integración scm (si paralelo) → Reviewer (máx. 2 vueltas) → Security Auditor (condicional) → PR/scm`. El hueco propuesto es entre Reviewer y Security Auditor; el cierre PR exige ambos aprobados (o iteración de CRs) antes de pushear `feature/<feature-id>`.
- **TDD + suite completa en integración:** Implementer escribe test-que-falla primero; `scm` corre la suite completa solo tras mergear worktrees paralelos. No hay hoy runner e2e ni browsers instalados en la plantilla.
- **Scripts npm por feature:** `test:template-hardening` muestra cómo exponer una suite sin imponerla globalmente.
- **CLI + SKILL token-eficiente (externo):** el README de `playwright-cli` posiciona CLI+SKILL como preferido para coding agents frente a MCP (sin schemas grandes ni accessibility trees en contexto); MCP queda para loops con estado persistente e introspección rica. `playwright-cli --help` es autocontenido para operación sin skills instaladas.
- **Plan especulativo versionado (externo):** `specs/*.plan.md` + seed test + tests generados uno-por-archivo es el flujo documentado; choca nominalmente con `specs/<feature>/requirements|design|tasks.md` del SDD (mismo directorio, distinto sufijo).

## 4. Riesgos detectados
- **No-fit por defecto en la plantilla:** el repo es plantilla SDD sin app web runnable ni servidor local; QA browser sin URL/seed/despliegue local no tiene qué probar. Sin guarda condicional, rompería features no-web y modo Quick.
- **Trigger sin definir:** no existe señal de `cuándo disparar QA` (paths UI, label en `feature_list.json`, campo en spec, presencia de URL/seed). El Leader hoy solo evalúa triggers de seguridad; añadir otra evaluación sin config versionada repite la deuda del mapa de seguridad (sin automatización que lo evalúe).
- **Flaky y tiempo:** selectores que derivan, waits/transiciones, datos que fugan entre runs, red, browsers headless vs. headed; el flujo heal documentado es iterativo y potencialmente largo (debug `tw-XXXX` + `attach/resume` + re-runs), en tensión con el límite de 2 vueltas del Reviewer.
- **Entorno browser pesado:** descarga de browsers, `userDataDir`, video/trace/screenshots, `PLAYWRIGHT_*` env, diferencias Windows/Linux/macOS y Git Bash/WSL; la plantilla ya tuvo incidentes de copia de `node_modules`/binarios por plataforma.
- **CI ausente:** sin workflows, QA solo correría localmente; llevarlo a CI exige matrix de browsers, caché, artefactos y tiempos (headless obligatorio, `PLAYWRIGHT_HTML_OPEN=never`).
- **Interactividad vs. autonomía:** `show`, `show --annotate` (pide al humano señalar algo) y el loop `attach/resume` presuponen humano o sesión persistente; en pipeline sin pausa hay que restringirse al subconjunto no-interactivo (`snapshot/find/eval/console/requests/screenshot/run-code` + `npx playwright test`).
- **Artefactos y trazabilidad:** nombre propuesto `reports/<feature>-qa.md` no existe; evidencias (png, pdf, mp4, traces, yml) necesitan convención de ruta/retención y reglas `.gitignore` (hoy `reports/` se ignora en destinos instalados); colisión `specs/*.plan.md` de Playwright con `specs/<feature>/` del SDD; inconsistencia preexistente `*-security.md` vs `*-security-audit.md` como advertencia de naming.
- **Seguridad/operación del browser:** `allowUnrestrictedFileAccess`, `SECRETS_FILE` dotenv, `allowedOrigins/blockedOrigins` (no son frontera de seguridad según docs), `route/unroute` mocking, `state-load` con cookies/storage, `--persistent` con perfiles reales; correr contra URLs externas en auditoría/CI requiere allowlist explícita.
- **Escalabilidad/opcionalidad:** dependencia global (`npm i -g`) vs. local (`npx`) sin lockfile en raíz; sin pin de versión de `@playwright/cli`/browsers los runs dejan de ser reproducibles; skill `qa` nueva suma superficie a mantener en tándem con upstream (`init-agents` se regenera en cada update de Playwright).
- **Solapamiento con etapas existentes:** QA que reabre código choca con `NUNCA editar código` de Reviewer/Security Auditor y con el conteo de vueltas (Reviewer máx. 2, Security 1 vuelta extra); sin regla de precedence, un `test.fixme`/spec-drift de Playwright puede contradecir `requirements.md`/`tasks.md`.
