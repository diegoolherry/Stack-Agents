# Findings — sdd-verify-phase

## 1. Archivos relevantes
- `.opencode/AGENTS.md` y `shared/AGENTS.md`: pipeline Full termina en `... → Preflight + Reviewer (máx. 2 vueltas) → Security Auditor (condicional) → PR + done`. No existe fase Verify independiente; la verificación contra spec vive dentro del Reviewer. Importa porque Verify debe insertarse sin duplicar ni romper el límite de 2 vueltas.
- `.opencode/agents/reviewer.md` + `.opencode/skills/reviewer/SKILL.md`: Reviewer de 2 pasadas obligatorias (P1 Negocio+Tests: RF-XX, trazabilidad RF→test, tasks completadas; P2 Calidad+ADRs+drift: CRAP>30, mutation break<60/high<80, tests, ADRs, drift con flag `architecture_drift`). Preflight degradable a revisión manual. Output `reports/<feature>-review.md` con veredicto APRUEBA/RECHAZA. Importa como solape directo con sdd-verify.
- `.opencode/agents/implementer.md` + `.opencode/skills/implementer/SKILL.md`: TDD RED→GREEN→REFACTOR por task de un área; corre solo tests unitarios de la feature; suite completa la corre el hook pre-Reviewer/integración scm; CRs (`changes/<feature>/<área>/CR-NNN.md`) por desvíos. Importa porque Verify debe leer tasks/CRs y evidencia de tests sin re-ejecutar el rol de implementador.
- `.opencode/skills/spec_author/SKILL.md`: baseline `requirements.md` (RF-XX/RNF/AC-XX), `design.md`, `tasks.md` (cada task con `área` + RF mapeado). Importa porque Verify necesita la matriz de cumplimiento RF/escenario→test.
- `.opencode/skills/scm/SKILL.md`: integración de Implementers paralelos (merge worktrees → suite completa → diff integrado al Reviewer). Importa porque Verify debe correr sobre el diff integrado, no sobre worktrees sueltos.
- `.opencode/skills/security_auditor/SKILL.md`: auditoría condicional por `scripts/security-trigger.config.json` (`reports/<feature>-security.md`). Importa como límite: Verify no audita seguridad (inyección/XSS/RLS); solo conformidad funcional.
- `scripts/security-trigger.config.json`, `architecture/architecture.md`, `feature_list.json` (`sdd-verify-phase/mode:full/pending`): contexto portable y trigger de seguridad; Verify no debe acoplarse a paths sensibles.
- Referencias externas verificadas vía webfetch (2026-09-07): `.../skills/sdd-verify/SKILL.md` v3.0 (`delegate_only:true`, secciones model-capable/model-small), `.../skills/judgment-day/SKILL.md` v1.7 (doble juez adversarial, fuera del camino Verify→Archive).

## 2. Patrones existentes
- **Patrón actual de verificación**: Reviewer ya verifica trazabilidad RF→test, ACs, tasks y corre tests (`npm test`/`dotnet test`/equivalente si no hay preflight). El hook pre-Reviewer corre todos los tests. Patrón reutilizable pero acoplado a calidad/drift.
- **Patrón de veredictos**: Reviewer APRUEBA/RECHAZA con motivos accionables; Security Auditor clasifica crítico (1 vuelta a Implementer) vs estructural (ADR, no bloquea). Patrón reutilizable para severidades de Verify.
- **Patrón anti-teléfono-descompuesto**: entregables en disco (`reports/`) + retorno de solo rutas; contadores independientes (vueltas Reviewer vs CRs).
- **Referencia gentle-ai observada sdd-verify v3.0 (factual)**:
  - Rol: sub-agente dedicado `sdd-verify`, quality gate independiente; ORCHESTRATOR GATE (orquestador delega, no ejecuta inline).
  - Contrato de activación: el orquestador provee estado estructurado (`sdd-status-contract.md`: schemaName, planningHome, changeRoot, artifactPaths, contextFiles, progreso tasks, dependencias, actionContext).
  - Reglas duras observadas: leer proposal+specs+design+tasks antes de juzgar (degradación documentada si faltan artefactos); si hay tasks pendientes → `blocked` sin suite completa; ejecutar tests reales (análisis estático solo nunca basta); escenario cumple solo con test covering que pasó en runtime; orden specs→design→tasks; no fija issues, solo reporta; construye report como bytes candidatos y corre `gentle-ai sdd-verify-validate` antes de escribir (si el validador falla/deniega, cero escrituras); primera línea debe ser fence ` ```yaml `; persiste según modo (Engram/openspec/hybrid/none); respeta `rules.verify` de `openspec/config.yaml`; no inicia 4R/Judgment Day/refuter/corrección (una contradicción = FAIL/escalación); estado de review es informativo, nunca prerrequisito (exit 125 reservado a prerrequisito real, no a falta de autoridad de review).
  - Gates de decisión observados: Strict TDD activo/inactivo; `workspace-planning` → STOP; tasks-only → solo completion; tasks+specs → sin coherencia design; incompletas core=Critical vs cleanup=Warning; test exit≠0=Critical; escenario sin covering test=CRITICAL UNTESTED/FAILING; desviación design=Warning salvo que rompa spec.
  - Pasos: cargar skills (Sección A), recuperar artefactos (Sección B), resolver modo testing/TDD, contar tasks, mapear requisito/escenario→evidencia+test, chequear design vs diff, correr test/build/type-check/coverage, matriz de compliance, persistir y retornar envelope Sección D. Referencias: `references/report-format.md`, `strict-tdd-verify.md` (solo si Strict TDD), `sdd-phase-common.md`.
  - Output: `## Verification Report` (change, modo, tabla completeness, evidencia build/tests/coverage, matriz spec, tablas correctness/design-coherence, issues CRITICAL/WARNING/SUGGESTION, veredicto `PASS | PASS WITH WARNINGS | FAIL`). Variante small-model retorna JSON mínimo `{status: pass|fail|warning, checks[], next: ready-for-archive|fixes-required}`.
  - Posición en flujo observado: `Apply → Verify (Q pasa→oferta RDD review opcional; Q falla→Apply) → Archive`; RDD/Judgment Day es posterior y opcional, nunca parte de Verify.
- **Referencia Judgment Day v1.7 (factual)**: herramienta standalone opt-in, dos jueces ciegos en paralelo sobre target inmutable, solo severos confirmados por ambos se fixean, máx. 2 rondas fix + 2 re-judgments, veredictos `APPROVED|ESCALATED`, sin autoridad de delivery. No equivale a Verify; es revisión adversarial posterior y explícita.
- **Contraste factual**: Stack-Agents mezcla verificación funcional + calidad + drift + seguridad-condicional en Reviewer(+Security Auditor). gentle-ai separa Verify independiente (requisitos/runtime, evidencia real) de review adversarial (Judgment Day/RDD) y de archive.

## 3. Dependencias afectadas
- **Directas**: `.opencode/agents/` (si se crea `verify.md` dedicado vs extender `reviewer.md`); `.opencode/skills/` (nueva skill `verify/` con `references/report-format.md` o extensión de `reviewer/`); `reports/` (nuevo `reports/<feature>-verify.md` separado de `<feature>-review.md` y `<feature>-preflight.md`); `specs/<feature>/` (requirements/design/tasks como entrada); `changes/<feature>/` (CRs como contexto).
- **Indirectas**: `.opencode/AGENTS.md` + `shared/AGENTS.md` (orden: `... Integración → Verify → Reviewer → Security Auditor` y presupuestos de vueltas); `feature_list.json` (sin cambio de schema); instaladores (distribución del nuevo agente/skill solo-opencode); `.claude/`/`.gemini/` no tocados por requisito.
- **Impacto en pipeline Full observado**: Verify correría sobre el diff integrado post-`scm` y pre-Reviewer. Reviewer pasaría a consumir `reports/<feature>-verify.md` como evidencia (hoy consume preflight opcional). Riesgo de doble ejecución de tests (Verify + hook pre-Reviewer + Reviewer manual) a documentar en spec.
- **Criterios escalables**: sin binario `gentle-ai sdd-verify-validate`/`sdd-archive-compose` (no portable); sin MCP Engram ni Context7; validación por convención + tests del proyecto (`npm test`/`dotnet test`/equivalente) + formato de reporte con hashes de salida (`test_output_hash`/`build_output_hash` como campos documentados, no como binario). Modos `engram/hybrid` = no-fit; equivalente portable = fichero en `reports/`.
- **Dependencias externas**: ninguna nueva. Test runners del proyecto destino, ya detectados por futuro `sdd-init` si existiera; hoy se resuelven por convención del repo destino.

## 4. Riesgos detectados
- **Solape Verify vs Reviewer P1**: ambos mapean RF/AC→tests y tasks. Si no se delimita, doble trabajo y veredictos contradictorios (Verify PASS + Reviewer RECHAZA por calidad/drift). Dato: Reviewer ya rechaza solo por problemas concretos, no por falta de preflight; esa tolerancia debeheredarse o delimitarse.
- **Riesgo de loop infinito**: gentle-ai lo corta con "Verify nunca inicia otro review/fix loop; contradicción = FAIL/escalación" y Reviewer local con máx. 2 vueltas. Sin regla equivalente, Verify→Implementer→Verify podría ciclarse; el presupuesto de vueltas debe definirse (p. ej. independiente del de Reviewer, como ya lo es CRs vs vueltas).
- **Riesgo de evidencia débil**: "static analysis alone is never verification" y "escenario cumple solo con covering test pasado en runtime". Hoy el Reviewer acepta revisión manual sin preflight. Endurecer a CRITICAL UNTESTED/FAILING puede chocar con repos sin suite; la degradación por artefactos faltantes (tasks-only / tasks+specs) debe copiarse.
- **Riesgo de validador nativo**: `sdd-verify-validate` con conteo autoritativo de requisitos/escenarios (`### Requirement:`/`### REQ-<n>:` + `#### Scenario:`) y fence YAML inicial no existe localmente. Portarlo como script sería un binario nuevo (tensión con "sin binarios"); dejarlo como convención pierde enforcement.
- **Riesgo de alcance**: Verify no debe auditar seguridad ni drift arquitectónico (ya cubiertos por Security Auditor/Reviewer P2) ni requerir transacción/ledger/receipt de RDD (gentle-ai lo prohíbe explícitamente). Mezclarlos lo convierte en segundo Reviewer.
- **Compatibilidad observada**: Verify independiente pre-Reviewer = **adaptar** (reporte separado, severidades CRITICAL/WARNING/SUGGESTION, veredictos PASS/PASS WITH WARNINGS/FAIL, evidencia de comandos+exit codes). Validador binario + Engram + fence YAML estricto + conteo nativo = **no-fit** sin adaptación. Judgment Day como sustituto de Verify = **no-fit** (es adversarial posterior, opt-in, sin autoridad de delivery).
- **Edge cases**: tasks pendientes → `blocked` (no suite completa); `workspace-planning` → STOP (sin equivalente local, debe definirse); repos sin runner (Strict TDD false → verify estándar, nunca cargar `strict-tdd-verify.md`); flaky tests (hashes de salida ayudan a trazabilidad pero no los resuelven).

- **Plan de spec sugerido (inputs para Spec Author, sin decisión de diseño)**:
  1. `requirements.md`: RFs — verificar completitud tasks (bloqueo si pendientes), corrección spec (matriz requisito/escenario→evidencia+test pasado en runtime), coherencia design (warning salvo rotura de spec), con degradación documentada por artefactos faltantes; RNFs — corre tests/build/type-check del proyecto con comandos+exit codes+hashes registrados; no fija código; severidades y veredictos cerrados; ACs verificables por dimensión.

- **Opciones observadas para Spec Author (mínimo 2, sin prescripción)**:
  - Opción A (adaptada de gentle-ai): agente+skill `verify` dedicados pre-Reviewer con reporte propio; máxima separación, mayor superficie y posible doble ejecución de tests.
